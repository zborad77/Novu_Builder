## 1. EXECUTIVE SUMMARY

### Co projekt je

NOVU Builder (interně FotoNabidka) je multi-tenant SaaS platforma pro generování stavebních nabídek pomocí AI vision analýzy fotografií. Technici na stavbě fotí poškozené objekty mobilní aplikací, backend analyzuje fotky AI modelem (Claude / OpenAI / mock) a generuje cenové nabídky ve formátech PDF/DOCX.

**Komponenty:**

| Komponenta          | Technologie                          | Stav                           |
| ------------------- | ------------------------------------ | ------------------------------ |
| Python backend      | FastAPI 0.135, SQLAlchemy 2, asyncpg | Primární — nejrozvinutější     |
| React frontend      | Vite + React                         | Prototyp / skeleton            |
| React Native / Expo | novu-mobile                          | Skeleton                       |
| Qt 6 Desktop (C++)  | CMake, Qt 6                          | Emerging — základní CRUD       |
| Nginx               | Alpine nginx                         | Docker proxy, cert placeholder |

### Reálná fáze vývoje

**Backend: Beta-ready / Production-ready pro single-tenant pilotní provoz.** Architektura je nadstandardní pro tuto fázi. Bezpečnostní hardening je výjimečně silný pro early-stage projekt.

**Celkový projekt: Prototyp se solidním backendovým jádrem** — frontend, mobile a desktop jsou skeletony.

### Celkové hodnocení architektury

Architektura je **nadprůměrně zdatná** pro projekt v této fázi. Backend vykazuje produkční myšlení: JWT revokace, refresh rotace, tenant isolation v repository vrstvě, audit trail, Prometheus metriky, Sentry integrace, CI pipeline. Největším rizikem není architektura, ale operační mezery (chybějící worker v docker-compose, backup, alerting) a několik konkrétních bezpečnostních mezer.

### Největší 5 přínosů

1. **Tenant isolation je hloubková** — `organization_id` je filtrovaná na DB vrstvě v každém repository dotazu, ne jen v routeru
2. **JWT revokace je kompletní** — jti blocklist v DB + `tokens_valid_after` na useru pro globální revokaci po změně hesla
3. **Audit trail je systematický** — middleware + explicitní `write_audit_log()` pro admin operace
4. **Fail-fast startup** — schema verze check, storage write probe, stale job recovery
5. **CI pipeline zahrnuje ruff + mypy (scoped) + bandit + pytest + živé smoke testy**

### Největší 5 rizik

1. **Worker není v docker-compose** — background AI analýzy neběží v produkčním deploymentu bez manuální akce
2. **`copy_storage_file` voláno bez `await`** — projekt duplikace tiše selhává (`python-backend/app/services/project_service.py:280`)
3. **`/metrics` a `/health` jsou unauthenticated** — bez nginx filtrace jsou veřejné
4. **Redis nemá heslo** v docker-compose — ovlivňuje bezpečnost per-account limiteru i job queue
5. **Duplicitní audit záznamy** — `AuditMiddleware` + `write_audit_log()` zapisují dvakrát pro totéž volání

## 3. SILNÉ STRÁNKY PROJEKTU

### Architektonické

**1. Tenant isolation na repository vrstvě**
Každý `repository.get_X()` přijímá `organization_id` parametr a přidává `WHERE organization_id = ?` podmínku. `resolve_org_id()` v deps.py fail-fastuje pokud non-superadmin nemá `organizationId`.
_Kde v projektu:_ `python-backend/app/repositories/project_repository.py:42`, `python-backend/app/api/deps.py:127`
_Přínos:_ SQL injection nebo chybná logika v routeru nemůže obejít tenant isolation — je enforce na nejnižší vrstvě.

**2. Startup fail-fast checks**
Schema version guard, storage write probe, DB connectivity check, stale job recovery. Aplikace odmítá startovat na nesprávném DB schématu.
_Kde v projektu:_ `python-backend/app/main.py:81–185`
_Přínos:_ Zabraňuje "silent broken production" po release.

**3. JWT architektura s kompletní revokací**

- `jti` v každém tokenu → `RevokedToken` tabulka
- Refresh token rotace (starý revokován, nový vydán)
- `tokens_valid_after` na useru → invalidace všech tokenů po změně hesla
- Impersonation tokeny jsou 15 min, označeny `impersonated_by`

_Kde v projektu:_ `python-backend/app/services/auth_service.py:82`, `python-backend/app/repositories/token_repository.py`

**4. Async storage s thread offloadem**
`asyncio.to_thread()` pro file I/O operace zabraňuje blokování event loopu.
_Kde v projektu:_ `python-backend/app/storage/local_photo_storage.py:123–155`

### Bezpečnostní

**5. Per-account brute-force ochrana**
Redis-backed counter, 10 pokusů / 15 min, fail-open (bez Redis platí per-IP limit).
_Kde v projektu:_ `python-backend/app/core/account_limiter.py`, `python-backend/app/api/routes/auth.py:35`

**6. Admin endpoint hardening**
Sanitizace error tracebacků, redakce file paths v `inputPayload`/`outputSummary`, truncace error messages na 500 znaků.
_Kde v projektu:_ `python-backend/app/api/routes/admin.py:237–329`

**7. Security headers middleware**
HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy — nastaveny automaticky na všechny response.
_Kde v projektu:_ `python-backend/app/main.py:251–262`

**8. Produkční config guards**
`model_validator` zabraňuje startu s `APP_DEBUG=True` nebo default `JWT_SECRET` mimo development.
_Kde v projektu:_ `python-backend/app/core/config.py:96–112`

### Testovací

**9. E2E tenant isolation testy**
17 scénářů přes real FastAPI ASGI stack s httpx. Žádné mocks — testuje se reálná auth, DB a isolation vrstva.
_Kde v projektu:_ `python-backend/tests/test_e2e_tenant_isolation.py`, `python-backend/tests/test_e2e_security_regression.py`

**10. CI s SAST a type checking**
bandit (medium+ severity), ruff, mypy (scoped na `app/core/` + `auth.py`), pytest + PostgreSQL v CI.
_Kde v projektu:_ `.github/workflows/ci.yml`

## 4. SLABÉ STRÁNKY A RIZIKA

### BEZPEČNOST

---

**[R-SEC-01] `/metrics` endpoint je unauthenticated**
_Priorita: Vysoká_
_Kde:_ `python-backend/app/api/routes/system.py:15`
_Problém:_ `GET /metrics` vrací Prometheus data bez jakékoliv autentikace. Komentář říká "MUST be firewalled at nginx/proxy layer" — ale nginx.conf není v repozitáři.
_Scénář útoku:_ Veřejně dostupný `/metrics` odhalí počty requestů, latence, počty jobů — business intelligence + stavová analýza bez přihlášení.
_Dopad:_ Únik provozních informací.
_Obtížnost zneužití:_ Trivial.
_Doporučení:_ Přidat HTTP Basic Auth nebo Bearer guard na `/metrics`, nebo whitelistovat IP na nginx vrstvě.
_Quick win:_ Ano.

---

**[R-SEC-02] `/health` endpoint odhaluje interní stav**
_Priorita: Střední_
_Kde:_ `python-backend/app/api/routes/system.py:43`
_Problém:_ `/health` vrací `startupChecks`, `debug`, počty running/queued jobs, `lastCompletedAt` — bez autentikace.
_Scénář útoku:_ Útočník sleduje `/health` pro detekci deployment momentu nebo zjistí počet queued jobs pro odhad zátěže.
_Doporučení:_ Oddělit `/alive` (unauthenticated liveness probe) od `/health` (autentikovaný detail). Nebo scrubovat citlivá pole.
_Quick win:_ Ano.

---

**[R-SEC-03] Redis bez autentikace v docker-compose**
_Priorita: Vysoká_
_Kde:_ `docker-compose.yml:19`
_Problém:_ Redis service nemá nastavené heslo (`requirepass`). Worker a account limiter komunikují přes nezabezpečenou Redis instanci.
_Scénář útoku:_ Útočník s přístupem do docker network může: (1) vymazat `auth:fail:*` klíče → obejít brute-force ochranu, (2) vložit falešné job payloady → worker zpracuje job s cizím `organization_id`.
_Dopad:_ Obejití bezpečnostních kontrol, potenciální cross-tenant data access přes worker.
_Obtížnost zneužití:_ Střední (vyžaduje přístup do docker network nebo exposed Redis).
_Doporučení:_ Přidat `REDIS_PASSWORD` env var, nastavit `--requirepass` v Redis config.
_Quick win:_ Ano.

---

**[R-SEC-04] Worker důvěřuje `organization_id` z Redis queue payload**
_Priorita: Střední_
_Kde:_ `python-backend/app/worker/runner.py:26`
_Problém:_ Worker přijímá `organization_id` z Redis payloadu a předá ho `AnalysisService.execute_job()`. Pokud je Redis kompromitován (viz R-SEC-03), útočník může enqueue job s `organization_id=None` (superadmin context) nebo s cizím org ID.
_Dopad:_ Cross-tenant data access při kompromitovaném Redis.
_Doporučení:_ Worker by měl načíst `organization_id` z DB (z projektu) místo z queue payloadu.

---

**[R-SEC-05] `copy_storage_file` voláno bez `await` — AKTIVNÍ BUG**
_Priorita: Kritická_
_Kde:_ `python-backend/app/services/project_service.py:280–284`
_Problém:_ `copy_storage_file` je `async def`, ale je volána bez `await` v `_duplicate_project_photos()`. Volání vytvoří coroutine objekt, který je okamžitě zahozán. Fyzické soubory se NEKOPÍRUJÍ. Pouze DB záznamy se vytvoří s odkazem na neexistující soubory.
_Dopad:_ POST /cases/{id}/duplicate vytvoří projekt s prázdnými foto záznamy → 404 při zobrazení fotek.
_Obtížnost exploitu:_ Trivial.
_Doporučení:_ Přidat `await` před `copy_storage_file(...)` na řádcích 280, 282, 284.

---

**[R-SEC-06] Audit log write failure je fail-open bez alertu**
_Priorita: Střední_
_Kde:_ `python-backend/app/core/audit.py:207–215`, `audit.py:266`
_Problém:_ `write_audit_log()` při selhání pouze loguje warning. Audit trail lze poškodit DB chybou bez viditelného dopadu na uživatele nebo alertu.
_Dopad:_ Ztráta auditní stopy bez detekce.
_Doporučení:_ Přidat Prometheus counter pro `audit_write_failed`, alertovat na nenulovou hodnotu.

---

**[R-SEC-07] Duplicitní audit záznamy pro admin operace**
_Priorita: Nízká_
_Kde:_ `python-backend/app/api/routes/admin.py:66–73` + `python-backend/app/core/audit.py:218–268`
_Problém:_ Admin endpointy volají `write_audit_log()` explicitně AND `AuditMiddleware` zapíše druhý záznam. Každá admin operace = 2 řádky v `audit_logs`.
_Dopad:_ Matoucí audit trail, dvojitý storage.

---

**[R-SEC-08] Admin password reset NENASTAVUJE `tokens_valid_after`**
_Priorita: Vysoká_
_Kde:_ `python-backend/app/api/routes/admin.py:193–230`
_Problém:_ `POST /admin/users/{id}/reset-password` změní heslo, ale NEnastaveí `tokens_valid_after`. Existující access tokeny resetovaného uživatele zůstávají platné až do přirozené expirace (60 min default).
_Scénář:_ Admin resetuje heslo kompromitovanému účtu → útočník má ještě 60 minut platný token.
_Doporučení:_ Nastavit `user.tokens_valid_after = datetime.now(UTC)` v endpoint handleru po úspěšné změně hesla.
_Quick win:_ Ano.

---

**[R-SEC-09] `_deny_counts` dict v audit.py je unbounded memory structure**
_Priorita: Nízká_
_Kde:_ `python-backend/app/core/audit.py:78`
_Problém:_ `_deny_counts: dict[str, tuple[float, int]]` roste s každým unikátním `user_id`. V dlouhodobém provozu s mnoha uživateli = memory leak.
_Doporučení:_ Použít `collections.OrderedDict` s LRU eviction nebo TTL-based cleanup.

---

**[R-SEC-10] Impersonation scope není explicitně omezen na read-only**
_Priorita: Střední_
_Kde:_ `python-backend/app/api/routes/admin.py:501–558`
_Problém:_ Impersonation token (15 min) je standardní access token. Blokován pouze v `require_superadmin()`. Ostatní write operace (patch case, upload foto) impersonaci nezablokují.
_Doporučení:_ Explicitně dokumentovat nebo přidat `scope: "impersonation"` claim a blokovat write operace dle záměru.

## 6. MAXIMÁLNÍ ZJEDNODUŠENÍ KÓDU BEZ ZTRÁTY FUNKČNOSTI

### SIMPLIFICATION OPPORTUNITY #1 — Duplicitní audit logging

**Aktuální stav:** Každá admin operace zapíše 2 audit záznamy:

1. `AuditMiddleware.dispatch()` — HTTP-level záznam
2. `write_audit_log()` v routeru — kontext-rich záznam

**Cílový stav:** Dvě strategie:

- **A)** Middleware loguje vše — přidat `detail` context z route metadat
- **B)** Přidat `request.state.audit_logged = True` v `write_audit_log()`, middleware to respektuje a přeskočí duplicitu

**Proč je to bezpečné:** Neměníme logiku, pouze redukujeme duplikaci. Výsledek = 1 záznam místo 2 per operace.
**Riziko změny:** Nízké.
**Postup:** Implementovat strategii B — nejmenší dopad na stávající kód.

---

### SIMPLIFICATION OPPORTUNITY #2 — Account limiter Redis connection pool

**Aktuální stav:** `python-backend/app/core/account_limiter.py` — každá funkce vytváří nový Redis klient (3 connection cycles per login).

**Cílový stav:** Předat existující Redis klient (`app.state.job_queue`) jako parametr do `is_account_throttled(email, redis)`, `record_login_failure(email, redis)`, `reset_login_failures(email, redis)`.

## 7. BEZPEČNOSTNÍ AUDIT

### Authentication

**JWT algoritmus:** HS256 — symetrický, přijatelný pro single-server setup. Při distributed deploymentu zvážit RS256.

**Token expiry:**

- Access: 60 minut (konfigurovatelné)
- Refresh: 30 dní (konfigurovatelné)

30denní refresh je poměrně dlouhý — kompromitovaný refresh token = 30 dní přístupu. Zmírňováno revokační tabulkou.

### Authorization / RBAC

**Capability model:** `ADMIN_CAPABILITIES` frozenset v `deps.py:99–124` — dobrý frameworking pro budoucí per-role rozšíření. Aktuálně všechno = superadmin only.

**Technician role:** Blokován přes `require_manager()`. Upload fotek a list cases jsou dostupné přes `get_current_user` — pravděpodobně záměrné.

### Tenant Isolation

**Hodnocení: Silná.** Org-scoped queries jsou konzistentní. E2E testy pokrývají 17 cross-tenant scénářů.

**Mezera:** Client isolation v `create_project()` — `clientId` není validováno vůči org.

### Token Revocation

**Revokace při logout:** Revokuje access i refresh token (jti do DB).
**Revokace při user change-password:** `tokens_valid_after` timestamp — elegantní bez nutnosti revokovat každý token.
**Revokace při admin reset-password:** CHYBÍ — viz R-SEC-08.
**Cleanup:** `delete_expired()` na startup — bez periodic cleanup. Doporučit cron task.

### Brute-Force Ochrana

**Per-IP:** slowapi, 10 req/minute na login.
**Per-account:** Redis counter, 10 pokusů / 15 min, fail-open.
**Mezera:** `change_password` volá `service.login()` interně — pokud je účet throttled, uživatel nemůže změnit heslo.

### Rate Limiting

**Login/refresh:** 10/minute per IP.
**Admin write:** 10/minute, sensitive: 5/minute.
**Ostatní endpointy (POST /cases, POST /images):** BEZ rate limitingu.
_Doporučení:_ Přidat rate limit na upload endpoint.

### Input Validation

**Pydantic v2:** Automatická validace request bodies.
**Filename sanitization:** `sanitize_filename()` — regex `[^a-zA-Z0-9._-]+` → bezpečné.
**Search input:** SQLAlchemy parameterized query — SQL injection bezpečné.
**MIME type validace fotek:** Chybí explicitní allowlist (JPEG, PNG, WEBP).
**Pillow decompression bomb:** Spoléhá na PIL default limit (89M px) — doporučit explicitní nastavení.

### File Upload / Download

**Upload size:** Limit `MAX_UPLOAD_SIZE_MB` (default 20 MB) — kontrolován v photo service.
**Path traversal:** Storage key je generována serverem (`time_ns() + uuid`), ne z user input. Bezpečné.
**Storage dev route:** `/mock-storage` mountována POUZE v development (`if settings.is_development`). Správné.

### ID Enumeration

**Project IDs:** `prj_{uuid4().hex[:8]}` — 8 hex chars = 2^32 možností. Tenant isolation zabrání přístupu k cizím projektům, ale ID jsou snáze odhadnutelná než full UUID.
_Doporučení:_ Zvážit delší suffix nebo full UUID.

### Admin Endpoint Hardening

**`/admin/logs`:** Čte log file z env-configured path — bezpečné.
**`/admin/audit`:** Parameterized queries — SQL injection safe.
**Impersonation:** Nelze impersonovat superadmina — správné.
**Reset-password:** Audit log + warning log, ale NENASTAVUJE `tokens_valid_after` — viz R-SEC-08.

### Dependency Risk

`requirements.txt` je pinned (`==`) — dobré pro reproducibility. Chybí automated vulnerability scanner.
_Doporučení:_ Přidat `pip-audit` do CI.

## 8. ROBUSTNOST A BUDOUCÍ ODOLNOST

### Při růstu počtu tenantů

- DB queries jsou org-scoped → lineárně škálovatelné
- Audit log roste globálně — přidat retention policy
- `_deny_counts` dict v audit.py roste s počtem unikátních user_ids — viz R-SEC-09

**Hardening:** Audit log archivace, TTL-based cleanup pro `_deny_counts`.

### Při růstu objemu dat

- Chybějící paginace je blocker — viz R-DB-02
- Chybějící DB indexy — viz R-DB-01

**Hardening:** Cursor-based paginace, DB indexy, partitioning `audit_logs` podle `created_at`.

### Při více background jobs

- Worker je single-threaded sequential loop — jeden job za druhý
- Při více worker instances: možný race condition při retry (žádný DB lock)

**Hardening:** Redis SETNX locking pro job execution, nebo Celery/Dramatiq.

### Při vyšší zátěži API

- Async FastAPI + asyncpg = horizontálně škálovatelný
- SQLAlchemy connection pool není explicitně nakonfigurován (default `pool_size=5`)

**Hardening:** Nastavit `pool_size`, `max_overflow` v `create_async_engine()`.

### Při chybách externích služeb (AI API)

- `_JOB_TIMEOUT_SECONDS = 180` — hard timeout pro AI call
- Chybí circuit breaker pro AI provider

**Hardening:** Exponential backoff s jitter v retry logice, circuit breaker pattern.

### Při partial outages (Redis down)

- Account limiter: fail-open (chybí per-account ochrana)
- Job queue: fail-open (joby nejsou enqueued bez alertu)
- Cache: fail-open (cache miss, přímý DB)

**Hardening:** Alert na Redis unavailability.

### Při rollback release

- Alembic `downgrade` je zdokumentován ale ne testován v CI

**Hardening:** Testovat `alembic downgrade -1` v CI.

### Při admin chybě (reset hesla bez revokace tokenů)

- Viz R-SEC-08 — `tokens_valid_after` není nastaveno po admin password reset

**Hardening:** Admin password reset MUSÍ nastavit `tokens_valid_after`, přidat email notifikaci uživateli.

## 11. ZÁVĚREČNÉ HODNOCENÍ

### Má projekt dobrý základ?

**Ano — výjimečně dobrý pro tuto fázi.** Backend je architektonicky solidní s produkčním myšlením, které není u early-stage projektů běžné. Tenant isolation, JWT architektura, audit trail a startup checks jsou implementovány na úrovni odpovídající real-world SaaS produktu.

### Je architektura životaschopná?

**Ano.** FastAPI + SQLAlchemy 2 + PostgreSQL + Redis je proven stack pro B2B SaaS aplikace. Async throughout umožňuje horizontální škálování. Repository pattern s org-scoped queries je správná abstrakce pro multi-tenant.

### Evolučně nebo větší refaktor?

**Evolučně — žádný větší refaktor není nutný.** Kritické opravy (A1–A5) jsou malé a lokalizované. Střednodobé úkoly (B1–B10) jsou standardní iterace. Architektura neutrpí žádnou strukturální vadou, která by vyžadovala rewrite.

### Kde je největší potenciál zlepšení?

1. **Operační připravenost** — worker v docker-compose, nginx config, backup, alerting
2. **Test coverage** — export flow, quote/measurement flow, file duplication bug, admin password reset
3. **Frontend/mobile** — backend je připraven, ale klientské aplikace jsou skeletony

### Co je největší překážka k robustní produkční verzi?

V pořadí dopadu:

1. **Worker není v docker-compose** — core feature nefunguje v produkci (30 min fix)
2. **Bug v duplikaci projektů** — tichá ztráta dat (15 min fix)
3. **Admin password reset nerevokuje tokeny** — bezpečnostní mezera (1 hod fix)
4. **Chybějící nginx.conf** — aplikace není dostupná přes HTTPS (2 hod fix)

Všechny čtyři jsou **quick wins** a blokují produkční nasazení.

## 1. SYSTEM OVERVIEW

Systém je **FastAPI backend** pro B2B SaaS platformu (řemeslné nabídky / stavební projekty). Stack: PostgreSQL 16 + Redis 7 + asyncpg + SQLAlchemy 2.0 + asyncio worker.

**Hlavní flow:**

```
HTTP Client
  → Nginx (TLS termination)
  → FastAPI (uvicorn, async)
      → API Routes (auth, cases, images, exports, analysis_jobs, work_catalog...)
      → Services (business logic)
      → Repositories (SQLAlchemy ORM)
      → PostgreSQL
      → Redis (job queue + brute-force throttle + cache)
  → Worker Process (standalone runner.py)
      → Redis LPOP (leased dequeue)
      → AI Provider (Claude / OpenAI / Mock)
      → PostgreSQL (job lifecycle: queued→running→completed/failed)
      → S3 / local storage
```

**Komponenty:**
- 2 DB engine pooly (API vs Worker — správná separace)
- Dual queue: `analysis:jobs` (AI analýza) + `heavy:jobs` (export, photo variants)
- Lease-based job ownership s Redis ZSET a reaper
- JWT (HS256) + DB revocation + `tokens_valid_after` guard
- Tenant isolation přes `organization_id` na každé úrovni
- Audit log middleware na security-critical operacích

## 2. CRITICAL FAILURE MAP

### 🔴 CRITICAL (P0)

---

**P0-1 — Scheduled retry promotion bypasses queue depth limit**

- **Soubor:** `python-backend/app/worker/queue.py` řádky 205–215
- **Kód:**
  ```python
  _PROMOTE_RETRY_SCRIPT = """
  local due = redis.call('ZRANGEBYSCORE', KEYS[2], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
  for _, raw in ipairs(due) do
      if redis.call('ZREM', KEYS[2], raw) == 1 then
          redis.call('RPUSH', KEYS[1], raw)   # <-- přímý RPUSH, bez limitu
      end
  end
  ```
- **Problém:** `promote_scheduled_analysis_jobs` přesouvá joby z retry ZSET přímo do hlavní fronty pomocí `RPUSH` bez kontroly kapacity (`_ENQUEUE_WITH_LIMIT_SCRIPT`). `enqueue_analysis_job` kontroluje `queue_depth + processing_depth + 1 > max_depth`, ale retry propagace tuto kontrolu obchází.
- **Scénář selhání:** 500 jobů selže, naplánují se na retry, reaper periodic loop (`promote_scheduled_analysis_jobs`) je všechny najednou promotuje → fronta přeroste nad `ANALYSIS_QUEUE_MAX_DEPTH` (default 1000). Worker pak zpracovává neomezeně jobů, přičemž API odmítá nové (`AnalysisJobQueueCapacityExceededError`). Redis paměť roste nekontrolovaně.
- **Dopad:** Queue overflow, OOM v Redis, degradace výkonu pro všechny tenanty.

**P0-2 — `change_password` obchází per-account brute-force guard**

- **Soubor:** `python-backend/app/api/routes/auth.py` řádky 154, 59–67
- **Kód:**
  ```python
  # auth.py:154 — change_password
  verified = await service.login(email=current_user.email, password=payload.currentPassword)
  # NENÍ před tím žádné is_account_throttled()!

  # Srovnání s /login (řádek 60):
  if await is_account_throttled(payload.email, settings.redis_url, redis_client=...):
      raise HTTPException(429, "Too many failed attempts.")
  ```
- **Problém:** `/auth/login` volá `is_account_throttled()` před jakýmkoliv DB dotazem. `/auth/change-password` volá `service.login()` (= bcrypt verify) přímo bez per-account throttle. Rate limit `@limiter.limit(get_settings().rate_limit_login)` je IP-based (10/min) — nestačí pro distribuované útoky.
- **Scénář selhání:** Útočník ukradne access token (XSS, token leak v logu, MITM bez HTTPS). Válídní token má 60 min životnost (default). Útočník zkouší change-password se stolen tokenem + slovníkovým útokem na `currentPassword`. Při 10 req/min × 60 min × počet IP = tisíce pokusů bez blokování per-account.
- **Dopad:** Kompletní převzetí účtu při kompromitaci access tokenu. Access tokeny nejsou okamžitě revokované po expiraci.

**P1-2 — Worker: unhandled exception ponechá lease bez akce a job ve stavu "running"**

- **Soubor:** `python-backend/app/worker/runner.py` řádky 609–674
- **Kód:**
  ```python
  async def _run_job_task(runtime: WorkerRuntime, lease: LeasedAnalysisJob) -> None:
      finalize_action = "none"
      try:
          result = await runtime.job_executor.execute_lease(...)
          finalize_action = "ack"
      except WorkerJobExecutionError as exc:
          logger.error("worker.job_unhandled_error", ...)
          # finalize_action ZŮSTANE "none" — lease se neackne, neretryne, nejde do DLQ
      except Exception as exc:
          logger.error("worker.job_task_error", ...)
          # totéž — finalize_action = "none"
      finally:
          if finalize_action == "ack":  ...
          elif finalize_action == "retry": ...
          elif finalize_action == "dlq": ...
          # "none" → žádná Redis ani DB akce
  ```
- **Problém:** Při jakékoli neočekávané výjimce (síťový výpadek k DB, asyncio.TimeoutError mimo AI volání, etc.) zůstane Redis lease v `analysis:processing` listě a DB job ve stavu `running`. Lease reaper to opraví až po `worker_job_lease_timeout_seconds` (default 600s). Pokud reaper neběží, job zůstane `running` navždy.
- **Scénář selhání:** Worker a DB jsou zdravé, ale S3 je dočasně nedostupný. `execute_job` selže při ukládání výsledku → `WorkerJobExecutionError` → lease dangling 10 minut → reaper requeue → opakování. Pokud S3 vypadl déle, job dostane max retry count a jde do DLQ, ale mezitím 10 min stagnuje.
- **Dopad:** Znatelné zpoždění recovery, job může být stuck 10+ minut bez viditelné příčiny.

**P1-3 — Redis fail-open: brute-force ochrana padá při výpadku Redis**

- **Soubor:** `python-backend/app/core/account_limiter.py` řádky 55–65
- **Kód:**
  ```python
  async def is_account_throttled(email, redis_url, *, redis_client=None) -> bool:
      client = redis_client or await _get_client(redis_url)
      if client is None:
          return False  # fail open — per-IP limit still applies
  ```
- **Problém:** Při výpadku Redis (restart, OOM, síťový split) celá per-account brute-force ochrana zaniká. Komentář říká "per-IP slowapi limit still applies" — ale `@limiter.limit("10/minute")` je taky Redis-backed (slowapi používá Redis pro rate limiting). Pokud Redis padne, padá OBOJE.
- **Scénář selhání:** Redis reboot trvá 30 sekund. Útočník v tu chvíli spustí distribuovaný brute-force na login endpoint. Žádná per-account ani per-IP ochrana. Stovky pokusů za 30 sekund.
- **Dopad:** Kompromitace účtů se slabými hesly během Redis výpadků. Nelze odhalit zpětně (counter se resetuje s Redis).

**P1-4 — DLQ přepisuje starší failure při opakovaném selhání**

- **Soubor:** `python-backend/app/worker/queue.py` řádky 179–203
- **Kód:**
  ```python
  _MOVE_TO_DLQ_SCRIPT = """
  ...
  redis.call('SET', KEYS[4], ARGV[4])  # SET — přepíše existující DLQ záznam
  ...
  """

  def _build_dlq_key(job_id: str) -> str:
      return f"{DLQ_KEY_PREFIX}{job_id}"  # jeden klíč per job_id
  ```
- **Problém:** DLQ je Redis `STRING` (ne list). Klíč je `analysis:dlq:{job_id}`. Pokud job selže → DLQ → admin requeue → selže znova → DLQ, druhý zápis přepíše první. Původní failure důvod, timestamp, `raw_payload` se ztratí.
- **Scénář selhání:** Job selže s timeout (recorded as DLQ), admin restartuje, job selže znova s jiným důvodem. Audit trail má jen poslední selhání. Debugging historicky selhávajících jobů je nemožný.
- **Dopad:** Ztráta auditovatelnosti u multi-failure jobů. Nelze zjistit root cause prvního selhání.

**P1-5 — Startup storage health scan je O(n souborů) — blokuje startup**

- **Soubor:** `python-backend/app/storage/local_photo_storage.py` řádky 62–63
- **Kód:**

**P1-6 — Login netlačí JTI nových tokenů do DB — nelze revokovat session bez logout**

- **Soubor:** `python-backend/app/services/auth_service.py` řádky 152–163
- **Kód:**
  ```python
  async def login(self, *, email, password) -> tuple | None:
      ...
      access_token, _, _ = self._create_access_token(user.id)
      refresh_token, _, _ = self._create_refresh_token(user.id)
  ```

## 3. DATA CONSISTENCY

---

**P1-7 — DB ↔ Redis queue nesoulad při worker crashu PŘED ack**

- **Soubor:** `python-backend/app/worker/runner.py` řádky 609–616, `python-backend/app/worker/queue.py` řádky 502–517
- **Scénář:** Worker dequeue → lease vytvoření (Redis) + DB `running` state. Worker zpracuje job, uloží výsledky do DB (`completed`), ale crashne PŘED `ack_analysis_job()`. Lease zůstane v `analysis:processing`. Reaper vidí expired lease, zkontroluje DB → job je `completed` → správně zahodí lease. Toto je pokryto. **ALE:** Pokud DB write (completed) selže a Redis ack selže → job je `running` v DB, lease je expired v Redis → reaper requeue → duplicitní zpracování. Race condition mezi reaper a worker.
- **Reálné riziko:** AI analýza je idempotentní (výsledky se přepíšou), ale dvojí volání AI API = dvojí náklady.

---

**P1-8 — ProjectPhoto: storage_key v DB vs. fyzický soubor — žádná transakční garance**

- **Pattern:** Upload → write to storage → uložit `storage_key` do DB. Pokud DB write selže po storage write, soubor existuje ale žádný DB záznam ho nesleduje → orphan file. Opačně: DB záznam bez souboru → broken URL. Storage consistency service (`check_storage_consistency.py`) toto detekuje ale neopravuje automaticky.
- **Dopad:** Orphan files v S3 rostou, nejsou čištěny. `pending_delete` state machine pomáhá, ale race condition při crash zůstává.

**P1-9 — Worker nemá healthcheck v docker-compose**

- **Soubor:** `docker-compose.yml` řádky 104–144
- Worker service má `restart: unless-stopped` ale žádný `healthcheck`. Docker neví, zda worker skutečně zpracovává joby nebo visí v deadlocku. Heartbeat TTL v Redis detekuje mrtvý worker, ale Docker orchestrator to neví.
- **Dopad:** Zombie worker procesy bez automatického detekování a restartu v zdravém stavu.

**P2-7 — `revoked_tokens` tabulka: každý request ověřuje JTI přes DB**

- **Soubor:** `python-backend/app/repositories/token_repository.py` řádky 60–70

**P2-8 — `AnalysisJob.input_payload` ukládá base64 data do PostgreSQL**

- **Soubor:** `python-backend/app/models/domain.py` řádek 263
- `input_payload: Mapped[str | None] = mapped_column(Text)` — JSON co šlo do AI. Pokud AI vstup obsahuje base64 obrázky, jeden záznam může být >1 MB. Tisíce jobů = GB dat v `analysis_jobs`. PostgreSQL Text column v hlavní tabulce zpomaluje sekvenční scany.
- **Dopad:** Tabulka `analysis_jobs` roste rychle, selecty jsou pomalejší i s indexy (dead tuples, VACUUM overhead).

**P2-9 — Chybí index na `revoked_tokens.expires_at`**

- `delete_expired()` dělá `DELETE FROM revoked_tokens WHERE expires_at <= ?` bez indexu na `expires_at`. Při tisících revokovaných tokenech = full table scan při cleanup.
- **Dopad:** Pomalý startup cleanup a scheduled cleanup při velkém objemu revokovaných tokenů.
